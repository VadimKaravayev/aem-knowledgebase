- [multi-author-scaling.md](multi-author-scaling.md) — Author-tier capacity drivers are parallel-author count + action types (not traffic/dispatcher-cache = publish concerns, not fail-safeness = HA concern). Whether there's a load balancer between authors depends on the NodeStore: TarMK doesn't support multi-node clustering, so "multi-author" means partitioning by tenant/team (no LB, direct routing); MongoMK lets multiple authors share one repo (LB makes sense, active-active). Gotcha: MongoMK-backed publish + fan-out replication agents → duplicate document errors.

- [ams-vs-aemaacs.md](ams-vs-aemaacs.md) — Adobe Managed Services (AMS) = managed hosting of classic AEM 6.5 Author/Publish/Dispatcher, fixed-size environments (manual resize requests), server access retained, service-pack updates, package-based licensing. AEMaaCS = SaaS, auto-scales both author and publish compute, no server access, continuous updates, combined CDN, usage-based licensing. Exam trap: "AMS + Cloud Manager/auto scaling" sounds cloud-native but Cloud Manager is CI/CD only — AMS cannot elastically scale; any scenario requiring traffic-spike or editor-load elasticity must answer AEMaaCS.

- [shared-datastore-binaryless-replication.md](shared-datastore-binaryless-replication.md) — Cloud migration pattern: point Author and Publish at the same blob store (S3/Azure Blob) so replication swaps binaries for hash-code references instead of moving bytes — only metadata replicates. Requires a shared `secret` config on every connected instance. Tradeoff: no storage isolation between tiers, so Data Store GC must check cross-instance references before deleting a binary. Exam signal: cloud migration + many DAM assets + frequent upload/update by editors → shared datastore + binary-less replication, not compute scaling (MongoDB) or plain maintenance (revision cleanup).

- [dispatcher-ignoreurlparams.md](dispatcher-ignoreurlparams.md) — Dispatcher `/ignoreUrlParams`: controls which query-string params are cache-relevant (distinct from `/filter`, which is request security, and `/rules`, which is path cacheability). Config shape is a glob allow/deny list like `/filter`, last-match-wins, `/type "1"` = ignore param for cache-key purposes. Two patterns: allowlist-the-ignorable (deny-all baseline + `1` for known tracking params) vs wildcard-ignore-all-deny-the-dynamic (`1` baseline + `0` for the few content-affecting params like search) — the latter is the exam-favored fix when campaign/tracking params vastly outnumber functional ones. Exam trap: offering a `/filter` change as the caching fix — `/filter` is security, not cache optimization.

- [translation-connector-cached-services.md](translation-connector-cached-services.md) — How to implement a translation connector's two JCR-backed hot-path services — the `translation_rules.xml` rules service and the cloud-config/credentials service — so their caches are correct on AEMaaCS. **A `ResourceChangeListener`-invalidated cache needs three mechanisms, not one:** (1) the `ExternalResourceChangeListener` marker, because AEMaaCS author is ≥2 pods on one repository and plain `ResourceChangeListener` "gets only local events" — an edit clears the cache on the writing pod only, so the rules report (routed request) and the XLIFF (Sling job, another pod) disagree, and nothing reproduces locally or on single-node on-prem; (2) an invalidation counter **sampled before the read** and stamped onto the cached value, because `updateAndGet` + `set(null)` loses an event that lands mid-read (a reader CASes null→stale onto an already-cleared cache); (3) a ~60 s TTL backstop for events never delivered at all. Registration traps: the marker does **not** extend `ResourceChangeListener` (implement both, keep registering under `ResourceChangeListener.class` — the marker alone deregisters the listener silently), and a listener with no `resource.paths` is ignored outright. Plus: no `synchronized` (AEM-15) — `AtomicReference` + `AtomicLong`; never cache the credentials failure fallback but do cache "no rules file" (cost: a 4-path `nodeExists` sweep per minute per pod); fetch the ruleset once per pass and thread it through the traversal; context-aware `/conf/<tenant>` lookup turns the cache into a keyed map whose invalidation must be global. Test recipe: aem-mock's `registerInjectActivateService` rejects a `now()`-overriding subclass (`NoScrMetadataException` → hand-wire with `FieldUtils.writeField`), the mid-read race is testable with zero threads via a one-shot `thenAnswer` that fires `onChange` during the load, and the marker needs its own `isAssignableFrom` guard test because nothing else can catch its removal. Implemented and unit-tested on the Crowdin connector, Sept 2026; translated.com's connector regressed the identical way.

- [i18n-dictionary-translation-target-path.md](i18n-dictionary-translation-target-path.md) — A translated i18n dictionary **cannot be written beside its source**: `/apps` and `/libs` are immutable at runtime on AEMaaCS, so `/apps/myproject/i18n/de.json` is an unwritable target and fails at import time, after the vendor has already returned the translation. Working rule: drop the `/apps`|`/libs` prefix and the `/i18n` segment, keep the rest, append `<lang>.json` (`/libs/wcm/core/i18n` → `/content/cq:i18n/wcm/core/zh.json`, observed from AEM's own `translation-job-service`). **i18n is the one content type whose target does not mirror its source**, so a connector that reuses language-copy logic for it produces an unwritable path for every dictionary; likewise a classification rule scanning only `/apps` and `/etc` never sees the authorable dictionaries the Translator creates.
