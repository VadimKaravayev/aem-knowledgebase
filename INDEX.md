- [server-sent-events-in-aem.md](server-sent-events-in-aem.md) — Pushing live updates to an author console without polling. AEM does not buffer an SSE response: `text/event-stream` plus `writer.flush()` and `resp.flushBuffer()` per frame streams immediately, chunked. A resource-type-bound servlet answers on any extension (`.sse`), and the login-token cookie carries auth since `EventSource` cannot send headers. Cost is exactly one parked Jetty request thread per stream (measured 1:1), which also holds a JCR session, so cap streams or use `startAsync()`. The trap: a loop with no lifecycle exit survives a bundle stop *and* restart, orphaned forever while keepalives make it look healthy — needs an `@Deactivate` flag (not an interrupt, banned by CQRules:GRANITE-54181) plus a duration cap. Reconnection is weaker than advertised: a non-200 permanently closes `EventSource`, so a redeploy's 404 kills the page until the client implements its own backoff retry. For a dashboard, one channel with a named-event envelope (`name`/`data`/`terminal`) and a bounded queue per subscriber using `offer`, never `put`.

- [multi-author-scaling.md](multi-author-scaling.md) — Author-tier capacity drivers are parallel-author count + action types (not traffic/dispatcher-cache = publish concerns, not fail-safeness = HA concern). Whether there's a load balancer between authors depends on the NodeStore: TarMK doesn't support multi-node clustering, so "multi-author" means partitioning by tenant/team (no LB, direct routing); MongoMK lets multiple authors share one repo (LB makes sense, active-active). Adobe's recommended AEM 6.5 multi-author topology = MongoMK author cluster (2+ instances/DB members) → TarMK publish farm. Gotcha: MongoMK-backed publish + fan-out replication agents → duplicate document errors.

- [revision-cleanup.md](revision-cleanup.md) — TarMK Online Revision Cleanup (default since 6.3), written for the results that look like failures. Three phases: estimation (**skips the whole run if the repo grew < 1 GB** since last compaction), compaction (full on Sundays, tail on weekdays, split by `full.gc.days` on `RevisionCleanupTask`; listing every day kills tail entirely), cleanup — and **disk is reclaimed only in the cleanup phase**, so a finished compaction with no size change is normal. Non-bugs: the **first ORC run reclaims nothing** (needs two generations), switching offline→online **doubles the repo** before settling back, and full compaction grows the repo before cleanup shrinks it (tail/full alternation sawtooths and delays reclamation). Hard aborts: free disk < **25%** of footprint (**not configurable**) and free heap < **15%** (`SegmentNodeStoreService#MEMORY_THRESHOLD`); size disks 2–3× the repo. Only revisions ≥ 24h old are eligible, and `SegmentNotFoundException` usually means app code held a reference past that 24h retention (a code bug, not a cleanup bug). Under write load ORC enters **forceCompact**, a write lock with a 1-minute timeout that yields to concurrent commits; healthy runs finish inside 2h. Monitor the `SegmentRevisionGarbageCollection` MBean (`EstimatedRevisionGCCompletion`, `startRevisionGC()`) and `TarMK GC #n:` log lines; the health check goes red only after **three consecutive cancellations** and **resets on restart**, so a routine restart erases the signal. Maintenance tasks run sequentially with no configurable order — give ORC its own window. Offline/oak-run is migration-only; oak-run must version-match Oak, `--force` is a one-way format upgrade, and `-Dsun.arch.data.model=32`/`-Dtar.PersistCompactionMap` are legacy. Windows never uses memory-mapped access — raise `segmentCache.size`. Sourced from the 6.4 doc, not reproduced locally.

- [tarmk-cold-standby.md](tarmk-cold-standby.md) — Warm-spare HA for the **Author** tier on TarMK (6.5/AMS only; AEMaaCS has no equivalent). Primary opens TCP 8023, standbys poll every `interval` (5s) for the head segment id and pull unknown segments; checksummed, auto-retrying, sync-only (a standby serves no user requests, only the OSGi console), and failover is **manual** (stop standby, pull primary from LB, restart standby with `-r primary,crx3,crx3tar`, build a new standby). Configured from `install.primary`/`install.standby` folders: `StandbyStoreService` (`mode`, `port`, `primary.host`, `secure` must match both sides, `interval`, `standby.autoclean`, `standby.readtimeout=60000`, `primary.allowed-client-ip-ranges`) + `SegmentNodeStoreService` (`standby=true`, `service.ranking=100` on the standby). Trap 1: leaving `org.apache.sling.installer.configuration.persist` true makes the standby sync the primary's own config down and stop being a standby. Trap 2: PIDs moved in 6.3, `oak.plugins.segment.*` → `oak.segment.*`, so older configs are silently ignored. Biggest gotcha: **no integrity checking**, corruption replicates faithfully — this is availability, not backup; explicitly not for Publish (publish farm instead) and not a capacity play (see multi-author-scaling.md). Monitor `SecondsSinceLastSuccess` on the `type="Standby"` JMX bean, not `Running`. With Online Revision Cleanup the primary runs all three phases and the **standby automatically runs the cleanup phase only** (estimation/compaction never run there, so compacting a standby by hand does nothing) — verify by comparing segmentstore sizes. Offline maintenance order: stop sync → compact primary → resume → `cleanup()` on standby; datastore GC primary first, then `startBlobGC()` on the standby (no RepositoryManagement bean there); hotfixes are re-cloned from the primary, never applied in place. Cost is negligible on the primary, single-threaded and CPU-heavy on the standby.

- [shared-datastore-binaryless-replication.md](shared-datastore-binaryless-replication.md) — Cloud migration pattern: point Author and Publish at the same blob store (S3/Azure Blob) so replication swaps binaries for hash-code references instead of moving bytes — only metadata replicates. - [dispatcher-ignoreurlparams.md](dispatcher-ignoreurlparams.md) — Dispatcher `/ignoreUrlParams`: controls which query-string params are cache-relevant (distinct from `/filter`, which is request security, and `/rules`, which is path cacheability). - [java-target-platform-vs-build-jdk.md](java-target-platform-vs-build-jdk.md) — Targeting an old Java platform from a new build JDK. - [httpclient-retries-timeouts-aem-connector.md](httpclient-retries-timeouts-aem-connector.md) — Apache HttpClient 4.5 is exported by **both** `aem-sdk-api` and `uber-jar` 6.5.22 (verified `unzip -l`, Sept 2026), so a connector needs no vendored HTTP client, just `org.apache.http.*;version=0.0.0` in bnd. **Do not hand-roll the retry loop:** `HttpRequestRetryHandler` covers connection failures (extend `DefaultHttpRequestRetryHandler` so its exception and idempotency rules still apply; with the default `requestSentRetryEnabled=false` a POST is replayed only if it never reached the server, which is what stops a token exchange being submitted twice) and `ServiceUnavailableRetryStrategy` covers `429`/`5xx`; never retry `4xx`. - [content-distribution-journal.md](content-distribution-journal.md) — **AEMaaCS publication is not replication**: Sling Content Distribution in **journal mode** (`org.apache.sling.distribution.journal`) — an ordered append-only log as an Adobe pipeline service *outside* AEM, with each publish pod an independent subscriber holding its own offset (so autoscaled/redeployed pods just replay to catch up; author never knows how many publishers exist). Five Kafka topics (`aemdistribution_package|status|discovery|command|event`); **`package` and `status` support 1 partition only** → strict ordering → **head-of-line blocking**, the mechanism behind every "blocked queue". Two levels of indirection people conflate: asset **binaries** never travel in the package (FileVault **binary-less mode** → references into the **shared Oak blob store**, same trick as [shared-datastore-binaryless-replication.md](shared-datastore-binaryless-replication.md) but built-in rather than configured), while the **package itself** rides *inside* the journal message (~<10 KB typical, 800 KB max) and only an oversized one is parked at `/var/sling/distribution/journal/packages` (12 h cleanup below min offset). Offsets are managed by agent code, **not** the log — stored under `/var/sling/distribution/journal/stores` in the **same atomic commit as the imported content** → exactly-once across pod replacement. **Diagnostic rule: the blocked queue renders on Author but the fault is on Publish** — items *are* queued, which proves export worked; an author-side fault fails at export and leaves the queue **empty**. The journal error queue **cannot retry** an item (unlike classic SCD) — remove it via Tools → Deployment → **Distribution UI**, then fix the content and republish. Service-user trap: publish imports as **`sling-distribution-importer`** (mapping `org.apache.sling.distribution.journal:importer`, defaults on `/content`,`/conf`,`/etc`, extend via repoinit per [repoinit-acls-on-apps-and-libs.md](repoinit-acls-on-apps-and-libs.md)) while author-side logs show `userId=replication-service`; and since the importer's is the only session on Publish, `jcr:createdBy`/`jcr:lastModifiedBy` there read as the service user — the original author is unrecoverable across that boundary, never build on it. **Exam vs. reality:** the cert answer for "pipeline timeout + blocked queues" is *importer lacks permissions on the Publish service* (distractors name the right symptom location, wrong tier) — but in production Adobe's own KBs say `AccessDeniedException` here *"possibly [has] no relation with the ACL / permissions"* (documented cause: `jcr:lockIsDeep` without `jcr:lockOwner`), `NamespaceException: Unknown namespace prefix` blocks queues too, and **content packages block it by themselves** (accesscontroltool #566, acs-aem-commons `ui.content` fix `58f4f4f`) — so check the blocking node before the ACLs. - [all-package-embed-structure.md](all-package-embed-structure.md) — The **assembly layer** of an AEM Maven project, i.e. everything past the well-known four-package split. Embed `<target>` is a fixed four-level grammar `/apps/<app>-packages/<application|content|container>/install[.author|.publish]` — level 3 is a *type* folder dictated by the embedded package's `packageType`, level 4 accepts **only** those two run-mode suffixes (you can scope OSGi config per environment, never a package embed), and the container's `definition/filter.xml` must cover the embed root or the zips build in and never install. The **`-packages` suffix is load-bearing**: without it the installer can treat subpackages as installables of the app it is installing → destructive cyclic installation, and nothing validates the name. Subprojects need `<cloudManagerTarget>none</cloudManagerTarget>` so only `all` deploys. **`ui.apps.structure`** is mandatory for every `packageType: application` and *not* for `content` — it is a build-time proof that no code package installs over another (and is why overriding the filter validator's `validRoots` doesn't break `/apps`). **The dependency trap:** a code package holding only OSGi bundles must NOT be declared as a dependency — bundle-only packages aren't registered with Package Manager, so it can never be satisfied and the symptom reads like a version mismatch on an artifact that demonstrably built. `ui.config` is `packageType: application` (OSGi config is code) rooted at `/apps/<app>/osgiconfig`. Vendor connectors ship their own `all`, embedded by the customer at the shared `/apps/vendor-packages/container/install` — so every package nested inside a vendor artifact must satisfy the cloud guidelines or it fails *the customer's* deploy, unfixable from their side. Plus: one package can't span `/apps` and mutable roots, containers can't use install hooks, Oak indexes ship as code because reindex precedes image switchover.
