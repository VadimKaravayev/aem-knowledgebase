## cloud-service/

AEM as a Cloud Service platform and Cloud Manager: architecture, programs, pipelines, publication, immutability, serverless extension points.

- [aemaacs-architecture-overview.md](cloud-service/aemaacs-architecture-overview.md) — Adobe's four architecture views of AEMaaCS condensed: **logical** (IMS tenant → program → prod/stage 1:1 same sizing, dev undersized, RDE without pipeline), **service** (Author + Document-based authoring feed a redesigned pub/sub Replication Service; AEM Publish and Edge Delivery Publish are co-existing origins behind one Adobe CDN; adjacent services table — Assets Compute, Testing, Data, Telemetry, IMS), **system** (author = pod cluster sharing one Oak repo; publish = farm, each pod its own repo + 1:1 Apache/dispatcher; preview = single node with expected downtime), **development** (five repo types, Cloud Manager mandatory, rolling updates). Four 6.x-breaking innovations with the design consequence of each. Exam checklist: perf/security tests on stage only, mixed /apps+/conf packages silently half-install, stale publish = blocked distribution queues not flush agents.
- [cloud-manager-program-types.md](cloud-service/cloud-manager-program-types.md) — Cloud Manager hierarchy (tenant → program → environments/repo/pipelines; **one production env per program**, so independently released sites need separate programs) and the two program types side by side. Full sandbox restriction list: no live traffic, **no auto-scaling (so no load testing)**, no custom domains/IP allow lists/extra regions/advanced networking/SLA, no automatic AEM updates, no runtime support, **hibernate after 8h idle, deleted after 3 months hibernated**; a pipeline still deploys to a hibernated sandbox. Adobe's decision table for mapping licensed Sites/Assets solutions to one combined program (2 dev + 2 RDE) vs separate programs (split when lifecycles or teams diverge; Connected Assets for raw creative work). Hibernation detail: idle = no author/preview/publish requests, **anyone with AEM product access can de-hibernate** (Developer Console), visitors get a landing page, pipelines *and* manual AEM updates apply while asleep, 3-month deletion removes **environments only** (program/repo/code kept). **Edit program** (Business Owner): add/remove Sites/Assets (effective **after next deployment**), Flexible Publish Tier beta, **WAF-DDOS checkbox** (licensed + checked + rules deployed via config pipeline; proof = `waf=` in CDN log `rules`), **CMK enable is irreversible** (keys in Experience Hub/Azure Key Vault). **Production program deletion is two-phase**: mark → credit refunded, environments removed, takedown window with dated Alert badge → permanent; unmark needs free credit. Sandbox delete is immediate.

- [cloud-manager-environments.md](cloud-service/cloud-manager-environments.md) — Environment-level Cloud Manager rules: **Production + Stage exist only as a pair** (no prod-only/stage-only, undeletable in production programs), Development takes **non-production pipelines only**, RDE has no pipeline, plus the **Specialized Testing Environment** for near-production stress tests. Roles: Business Owner adds/edits (incl. regions), Deployment Manager or BO updates/deletes dev, Developer opens Dev Console. **Name and primary region are immutable.** Up to 3 additional publish regions, set on production and shared with stage, add/remove in separate transactions, provision advanced networking *first* or extra-region traffic exits via the primary proxy; auto-recovery, traffic to nearest online region. **Preview service is blocked by a default `Preview Default [<envId>]` IP Allow List** until you apply your own and unapply it. Sandbox/dev AEM updates are **two steps: update the pipeline version, then run it**; no pipeline, no update. Custom domains: Sites publish+preview; IP allow lists: Sites author+publish+preview.
- [cloud-manager-ssl-certificates.md](cloud-service/cloud-manager-ssl-certificates.md) — Cloud Manager TLS for custom domains: **Adobe-managed DV** (Let's Encrypt, auto-renew every 3 months, prod *and sandbox*, **CNAME must stay or renewal fails and the site goes down**, 5 issuances/hostname-set/7 days) vs **customer-managed OV/EV** (you upload; DV and self-signed rejected; RSA **2048 only**, EC P-256/P-384, **ECDSA recommended**; key in PKCS#8, PEM files; one cert may serve several envs; wildcards ok). Limits: **70 certs/program incl. expired, 100 SANs/cert**. Platform TLS picks "most specific + most recently deployed" so overlapping wildcard + specific certs misbehave; cert must exist before a domain can be added. OpenSSL PFX/P7B/DER→PEM and local `openssl verify` recipes. UI flow: domain → cert → CDN config; **Business Owner/Deployment Manager only**; three paste fields (cert, PKCS#8 key, chain) and **leaf cert in the chain field = upload fails**; DV verifies domain *before* cert, OV/EV *after*. Lifecycle: green ≥14 d / orange <14 d (UI notifications only) / red expired; View and Update applies immediately; **delete needs a pipeline run to undeploy** and a DV cert with active domains cannot be deleted.
- [cloud-manager-custom-domain-names.md](cloud-service/cloud-manager-custom-domain-names.md) — Cloud Manager **Domain Settings** (Services menu; Business Owner/Deployment Manager; Sites programs, publish+preview, not sandbox). Order by cert type: **DV = domain → Verify via CNAME/A record (hours) → DV cert → mapping**; **OV/EV = domain → OK → cert → marked Verified → mapping**; own cert + own CDN → skip SSL page, straight to Domain Mapping. Adobe CDN users still register the domain. DNS: subdomain **CNAME → `cdn.adobeaemcloud.com`**, apex **four A records 151.101.{3,67,131,195}.10**; **www and apex are separate entries**. "Register before you advertise": DNS last, after the mapping, to avoid outages and **domain takeover**; DV domains go live at verification so do it at cutover. Overlap rule: most specific cert, then most recently updated. **TXT record** `_aemverification.<domain>` = `adobe-aem-verification=<domain>/<programId>/<envId>/<uuid>`: revocable authorization binding hostname → environment, routes nothing, verify with `dig -t txt`; removed from the current UI page (June 2026) but still in the Cloud Manager API (`dnsTxtRecord`/`dnsZone`, prod Sites programs only) and older exam material.

- [cloud-manager-variables.md](cloud-service/cloud-manager-variables.md) — Three Cloud Manager variable mechanisms, routinely conflated: **build env vars CM sets** (`CM_BUILD` — the "am I in CM?" switch, `CM_PROGRAM_ID/NAME`, `CM_PIPELINE_ID/NAME`, `CM_AEM_PRODUCT_VERSION`, `ARTIFACTS_VERSION`) with the two Maven activation idioms (`env.CM_BUILD` = only inside CM, `!env.CM_BUILD` = only local — the `!` form is the classic copy-paste trap; `env.` prefix required, `STAGE.CM_BUILD` never activates); **custom pipeline variables** you set via `aio cloudmanager:set-pipeline-variables` (`--variable`/`--secret`, masked in logs, build-only — e.g. private Maven repo credentials); **runtime environment variables** per environment (UI or `set-environment-variables`), consumed as `$[env:VAR]` / `$[secret:VAR]` in OSGi, uppercase/underscore names, no `INTERNAL_`/`ADOBE_` prefix, no pipeline run needed. Rule: `CM_*` = build facts given, pipeline vars = build values you give, env vars = runtime values; run modes pick the config file, variables fill its values.
- [aemaacs-content-package-structure.md](cloud-service/aemaacs-content-package-structure.md) — The AEMaaCS Maven structural contract: **ui.apps** (`application`, `/apps` only) / **ui.content** (`content`, mutable) / **ui.config** (`application`, `osgiconfig` + repoinit) / **all** (container, **the only package Cloud Manager deploys** — everything else sets `cloudManagerTarget=none`). Container rules: **`<embeddeds>` never `<subPackages>`**, embed path `/apps/<app>-packages/(application|content|container)/install[.author|.publish]` — **the `-packages` suffix is load-bearing** (keeps embeds outside real code packages' filters; targeting `/apps/my-app/install` = self-clobbering), container filter.xml must include the embed root, zip=packages jar=bundles, clean-plugin on `initialize` against stale embeds. **Repository structure package: required for every `application` package, never for content** (enforces cross-package structural correctness). Dependencies: mutable→immutable (`ui.content`→`ui.apps`; bundles-only packages get none). `/oak:index` mutable at runtime but **ships as code** (pre-cutover reindex). **Repoinit = inline `scripts` in a `.config` factory config — `references` doesn't work.** Third parties: embed the vendor's **`all`**, from a declared Maven repo. `AccessControlHandling=merge` typical. Docs-based Oct 2026.
- [aemaacs-osgi-configuration.md](cloud-service/aemaacs-osgi-configuration.md) — Cloud OSGi config contract. **`.cfg.json` only** (factory `~name`), in `ui.config` under `config.<runmode>`, **not browsable under `/apps` on cloud** (Developer Console instead). **Preview tier inherits publish OSGi config — no `config.preview` folder**; vary preview only via a service-bound variable. Decision ladder: **inline = standard** (Git-versioned, tied to deploys) → `$[env:NAME;default=…]` only for dev/preview variation (**Adobe recommends against non-secret env vars on stage/prod**) → `$[secret:NAME]` anywhere. **Placeholders don't work in repoinit.** Variable rules: names 2–100 chars `[a-zA-Z_][a-zA-Z_0-9]*`, values ≤ 2048, **≤ 200/environment**, reserved `INTERNAL_/ADOBE_/CONST_`, **`AEM_` = product's public prefix**; per-tier values via the API/CLI `service` param (author/publish/preview) over name prefixes; empty value = delete; API needs Deployment Manager. Variable deploys **restart author+publish in minutes with NO quality gates**, can fail while any pipeline runs, and **variables aren't versioned** → additive strategy (new name, not new value; delete days later) + set vars before the dependent code deploy. Local dev: env vars via export; **secrets = extension-less files in `secretsdir`** (`org.apache.felix.configadmin.plugin.interpolation.secretsdir` in sling.properties) — a `.txt` extension is why the placeholder resolves empty. Authoring recipe: local web console → **OSGi Installer Configuration Printer, "OSGi Configurator JSON"** → paste into `ui.config` (console writes .cfg.json into the repo as a side effect); verify on cloud via Developer Console Status Dump → Configurations. Docs-based Oct 2026.

- [cloud-manager-code-quality-testing.md](cloud-service/cloud-manager-code-quality-testing.md) — The code-quality gate's scoring model: **SonarQube 9.9 + OakPAL**, 100+ rules. Tiers: **Critical = immediate fail; Important = pause + override — but NOT overridable in code-quality-only pipelines** (PR-check consequence: important finding = failed check); Info = nothing. Thresholds (verbatim): **Security < B critical, Reliability < D critical, Maintainability < A important, Coverage < 50% important**; Info = skipped tests > 1, open issues > 0, duplicated lines > 1%, cloud compatibility > 0. **The asymmetry: one *major* vulnerability fails the pipeline (Security < B) but it takes a *blocker* bug (Reliability < D)**; one smell past 5% remediation cost pauses it (Maintainability < A). Ratings A–E = none/minor/major/critical/blocker; maintainability by remediation cost ≤5/10/20/50%. **AMS differs in exactly two cells: Reliability = Important < C (vs Critical < D on cloud) and no Cloud Service Compatibility metric**; AMS names the override roles (deployment/project lead, business owner; override has a timeout). False positives: plain `@SuppressWarnings("squid:S2068")` method/class level, no Adobe mechanism. Docs-based Oct 2026, metrics cross-checked, both platform pages.

- [cloud-manager-git-repositories.md](cloud-service/cloud-manager-git-repositories.md) — The three ways a Cloud Manager pipeline gets a Git repo, and which to pick: **Adobe repository** (push to `git.cloudmanager.adobe.com`), **private repository / BYO GitHub** (pipelines read your github.com repo directly), **external repository** (any HTTPS Git host). Adobe-hosted and private are alternatives, not a combination — with BYO there is nothing to push to Adobe, and running both means two sources of truth. **The limit to check first:** BYO is *"exclusive to public GitHub. Support for self-hosted GitHub is not available"* — GHE must use *external* instead, and an SSH host alias in `~/.ssh/config` (`git@github.mycompany:org/repo.git`) disguises which one you actually have. BYO setup: a GitHub **org owner** (not a developer) installs `github.com/apps/cloud-manager-for-aem` → Add Repository → Private Repository (URL must end `.git`) → **Generate** the secret, **shown once**, regenerate is the only recovery → commit it to **`.well-known/adobe/cloud-manager-challenge` on the default branch** → Validate; red icon and unusable until then, and a repo with **no commits cannot be validated** (challenge is fetched from the default branch). Payoff is PR-time full-stack code-quality checks reported as GitHub checks. One challenge value per program, one path — a repo can't be validated against two programs. Adobe-repo credentials live in **Access Repo Info** (Developer/Deployment Manager roles): a Git-specific username/password, **not** Adobe ID/SSO, and regenerating invalidates the old one everywhere (stale keychain entries are the usual "sudden auth failure"). - [ams-vs-aemaacs.md](cloud-service/ams-vs-aemaacs.md) — Adobe Managed Services (AMS) = managed hosting of classic AEM 6.5 Author/Publish/Dispatcher, fixed-size environments (manual resize requests), server access retained, service-pack updates, package-based licensing. - [content-distribution-journal.md](cloud-service/content-distribution-journal.md) — **AEMaaCS publication is not replication**: Sling Content Distribution in **journal mode** (`org.apache.sling.distribution.journal`) — an ordered append-only log as an Adobe pipeline service *outside* AEM, with each publish pod an independent subscriber holding its own offset (so autoscaled/redeployed pods just replay to catch up; author never knows how many publishers exist). Five Kafka topics (`aemdistribution_package|status|discovery|command|event`); **`package` and `status` support 1 partition only** → strict ordering → **head-of-line blocking**, the mechanism behind every "blocked queue". Two levels of indirection people conflate: asset **binaries** never travel in the package (FileVault **binary-less mode** → references into the **shared Oak blob store**, same trick as [shared-datastore-binaryless-replication.md](infrastructure-ops/shared-datastore-binaryless-replication.md) but built-in rather than configured), while the **package itself** rides *inside* the journal message (~<10 KB typical, 800 KB max) and only an oversized one is parked at `/var/sling/distribution/journal/packages` (12 h cleanup below min offset). Offsets are managed by agent code, **not** the log — stored under `/var/sling/distribution/journal/stores` in the **same atomic commit as the imported content** → exactly-once across pod replacement. **Diagnostic rule: the blocked queue renders on Author but the fault is on Publish** — items *are* queued, which proves export worked; an author-side fault fails at export and leaves the queue **empty**. The journal error queue **cannot retry** an item (unlike classic SCD) — remove it via Tools → Deployment → **Distribution UI**, then fix the content and republish. Service-user trap: publish imports as **`sling-distribution-importer`** (mapping `org.apache.sling.distribution.journal:importer`, defaults on `/content`,`/conf`,`/etc`, extend via repoinit per [repoinit-acls-on-apps-and-libs.md](cloud-service/repoinit-acls-on-apps-and-libs.md)) while author-side logs show `userId=replication-service`; and since the importer's is the only session on Publish, `jcr:createdBy`/`jcr:lastModifiedBy` there read as the service user — the original author is unrecoverable across that boundary, never build on it. **Exam vs. reality:** the cert answer for "pipeline timeout + blocked queues" is *importer lacks permissions on the Publish service* (distractors name the right symptom location, wrong tier) — but in production Adobe's own KBs say `AccessDeniedException` here *"possibly [has] no relation with the ACL / permissions"* (documented cause: `jcr:lockIsDeep` without `jcr:lockOwner`), `NamespaceException: Unknown namespace prefix` blocks queues too, and **content packages block it by themselves** (accesscontroltool #566, acs-aem-commons `ui.content` fix `58f4f4f`) — so check the blocking node before the ACLs. AEMaaCS only; 6.5/AMS still uses replication agents. Apache distribution-journal docs + Adobe KB ka-21668/ka-23465, Sept 2026.
- [rolling-deployment-two-version-overlap.md](cloud-service/rolling-deployment-two-version-overlap.md) — An AEMaaCS deploy is rolling: **old and new code serve traffic simultaneously**, and mutable content lands only after switchover, so "my new code and my new repo state arrive together" is never true. Mutable install order is **pre-startup** (index definitions) → **during startup** (service users, ACLs, node types — where repoinit runs, on a repo with no package content yet, see repoinit-acls-on-apps-and-libs.md) → **post-switchover** (everything else via Vault). Three consequences: (1) **spread service-user/ACL changes over two releases** (add the grant in N, switch code and remove the old one in N+1) or old nodes hit `LoginException`/`AccessDeniedException` mid-deploy; (2) **a rollback restores code but NOT content** — mutable structures from the failed release survive, so old readers must tolerate them or you fix forward; (3) **indexes set deploy duration** (reindex happens before the traffic shift, and both old and new index definitions must be serviceable during the overlap; ACS Commons Ensure Oak Index doesn't work on AEMaaCS). Reference facts: run modes are a **closed set** (`author`/`publish` × `rde`/`dev`/`stage`/`prod`, no custom ones, no per-environment package scoping); Cloud Manager packages are frozen with a **`cp2fm`** suffix (no rebuild/reinstall/download); manual one-off installs are **mutable-only and time out at 10 minutes** — the **"undefined" error is the request limit, not a failure: install continues in background, never retry** (the retry is what conflicts); **no FileVault install hooks in immutable packages** (mutable post-switchover packages DO support them); a **mixed** package installs only its mutable half silently at runtime (build log does warn `is of MIXED type`); **`getRunModes()` loses the environment type at runtime** — env dimension exists only for OSGi config resolution, branch via a config property; third-party packages via remote Maven repo or committed filesystem Maven repo, must pass cloud validation; OSGi *and* maintenance-task config must live in source control (Tools → Operations is gone). From the Adobe deploying-overview page, not reproduced against a live pipeline.
- [repoinit-acls-on-apps-and-libs.md](cloud-service/repoinit-acls-on-apps-and-libs.md) — **Myth killed:** "`/apps`/`/libs` are immutable on AEMaaCS so repoinit can't set ACLs there; permissions must ship as `rep:policy` in `ui.apps`." ## infrastructure-ops/

- [multi-author-scaling.md](infrastructure-ops/multi-author-scaling.md) — Author-tier capacity drivers are parallel-author count + action types (not traffic/dispatcher-cache = publish concerns, not fail-safeness = HA concern). Whether there's a load balancer between authors depends on the NodeStore: TarMK doesn't support multi-node clustering, so "multi-author" means partitioning by tenant/team (no LB, direct routing); MongoMK lets multiple authors share one repo (LB makes sense, active-active). Adobe's recommended AEM 6.5 multi-author topology = MongoMK author cluster (2+ instances/DB members) → TarMK publish farm. Gotcha: MongoMK-backed publish + fan-out replication agents → duplicate document errors.
- [revision-cleanup.md](infrastructure-ops/revision-cleanup.md) — TarMK Online Revision Cleanup (default since 6.3), written for the results that look like failures. Three phases: estimation (**skips the whole run if the repo grew < 1 GB** since last compaction), compaction (full on Sundays, tail on weekdays, split by `full.gc.days` on `RevisionCleanupTask`; listing every day kills tail entirely), cleanup — and **disk is reclaimed only in the cleanup phase**, so a finished compaction with no size change is normal. Non-bugs: the **first ORC run reclaims nothing** (needs two generations), switching offline→online **doubles the repo** before settling back, and full compaction grows the repo before cleanup shrinks it (tail/full alternation sawtooths and delays reclamation). Hard aborts: free disk < **25%** of footprint (**not configurable**) and free heap < **15%** (`SegmentNodeStoreService#MEMORY_THRESHOLD`); size disks 2–3× the repo. Only revisions ≥ 24h old are eligible, and `SegmentNotFoundException` usually means app code held a reference past that 24h retention (a code bug, not a cleanup bug). Under write load ORC enters **forceCompact**, a write lock with a 1-minute timeout that yields to concurrent commits; healthy runs finish inside 2h. Monitor the `SegmentRevisionGarbageCollection` MBean (`EstimatedRevisionGCCompletion`, `startRevisionGC()`) and `TarMK GC #n:` log lines; the health check goes red only after **three consecutive cancellations** and **resets on restart**, so a routine restart erases the signal. Maintenance tasks run sequentially with no configurable order — give ORC its own window. Offline/oak-run is migration-only; oak-run must version-match Oak, `--force` is a one-way format upgrade, and `-Dsun.arch.data.model=32`/`-Dtar.PersistCompactionMap` are legacy. Windows never uses memory-mapped access — raise `segmentCache.size`. Sourced from the 6.4 doc, not reproduced locally.
- [tarmk-cold-standby.md](infrastructure-ops/tarmk-cold-standby.md) — Warm-spare HA for the **Author** tier on TarMK (6.5/AMS only; AEMaaCS has no equivalent). Primary opens TCP 8023, standbys poll every `interval` (5s) for the head segment id and pull unknown segments; checksummed, auto-retrying, sync-only (a standby serves no user requests, only the OSGi console), and failover is **manual** (stop standby, pull primary from LB, restart standby with `-r primary,crx3,crx3tar`, build a new standby). Configured from `install.primary`/`install.standby` folders: `StandbyStoreService` (`mode`, `port`, `primary.host`, `secure` must match both sides, `interval`, `standby.autoclean`, `standby.readtimeout=60000`, `primary.allowed-client-ip-ranges`) + `SegmentNodeStoreService` (`standby=true`, `service.ranking=100` on the standby). Trap 1: leaving `org.apache.sling.installer.configuration.persist` true makes the standby sync the primary's own config down and stop being a standby. Trap 2: PIDs moved in 6.3, `oak.plugins.segment.*` → `oak.segment.*`, so older configs are silently ignored. Biggest gotcha: **no integrity checking**, corruption replicates faithfully — this is availability, not backup; explicitly not for Publish (publish farm instead) and not a capacity play (see multi-author-scaling.md). Monitor `SecondsSinceLastSuccess` on the `type="Standby"` JMX bean, not `Running`. With Online Revision Cleanup the primary runs all three phases and the **standby automatically runs the cleanup phase only** (estimation/compaction never run there, so compacting a standby by hand does nothing) — verify by comparing segmentstore sizes. Offline maintenance order: stop sync → compact primary → resume → `cleanup()` on standby; datastore GC primary first, then `startBlobGC()` on the standby (no RepositoryManagement bean there); hotfixes are re-cloned from the primary, never applied in place. Cost is negligible on the primary, single-threaded and CPU-heavy on the standby.
- [filevault-workspace-filter.md](infrastructure-ops/filevault-workspace-filter.md) — `META-INF/vault/filter.xml` authoritative semantics. **`mode`**: `replace` (default — **deletes**) / `merge_properties` (add-only) / `update_properties` (add+update, no delete); **`merge`/`update` are deprecated aliases** most advice still names; `type="cleanup"` = ignored by package-type detection/orphan validation. Rules: `pattern` = **regex on the full JCR path** (not glob), `matchProperties="true"` (≥ 3.1.28) filters **properties**; **sequential, LAST match wins, and the first rule's type sets the default** (include-first → default exclude). **The install state matrix: covered + in-repo + NOT in package = REMOVED** (the "package deleted my content" incident) and **in package but uncovered = silently never installs**. Same filter drives export (what's serialized) and import (what's owned/removed) — editing it for a convenient export changes what the install deletes. Uncovered ancestors: `.content.xml` type, else parent default/`nt:folder` (≥ 3.4.4). Jackrabbit docs Oct 2026.
- [filevault-validation-compliance.md](infrastructure-ops/filevault-validation-compliance.md) — wcm.io field guide to the validator suite filevault-package-maven-plugin ≥ 1.1.0 runs on every build. **Step zero: which validations run depends on `packageType`** — fix the type (application/content/container; avoid `mixed`, split instead = AEMaaCS-readiness) before chasing errors; app content in `/etc` → `/apps`. - [package-manager.md](infrastructure-ops/package-manager.md) — Package Manager **semantics** (6.5): FileVault zip = **state at build time, no version history**. **Snapshots**: install auto-snapshots what it overwrites, **uninstall = reinstall the snapshot** (revert, not remove); **Extract Only → no snapshot → uninstall impossible**; **Delete removes the package entity only, content stays** (≠ uninstall, both directions). - [thread-dump-analysis.md](infrastructure-ops/thread-dump-analysis.md) — AEM auto-collects thread dumps (`crx-quickstart/threaddumps/<YYYYMMDD>/threaddump.<HHMMSS>.txt.gz`), **enabled by default on both 6.5 and AEMaaCS** via `com.adobe.granite.threaddump.impl.ThreadDumpCollector` (verified identical defaults on `com.adobe.granite.threaddump-1.0.36` on-prem + cloud SDK): `scheduler.period=60`, `dumpsPerFile=10` → **each file is 10 concatenated dumps, not one** (split on the timestamp/`Full thread dump` headers or every count is 10× inflated); `maxBackupDays=7` so grab files before rotation. **Gotcha 1:** `enableJStack=false` by default → dumps come from **ThreadMXBean, not jstack**, so every thread shows `nid=0xffffffff` and `tid` is a sequential `Thread.getId()` — **`top -H` correlation is impossible**; flip `granite.threaddump.enableJStack=true` (needs a JDK) or take your own `jstack`/`jcmd Thread.print`. **Gotcha 2:** that rendering emits `- waiting to lock <0x…> owned by "null" tid=0x-1` for *parked* threads — one real file had **1929 such lines and zero `BLOCKED`**, because `ThreadPoolExecutor.getTask()`→`LinkedBlockingQueue.take()` is an **idle worker**; never grep `waiting to lock` to measure contention. Method: split → trend thread count → state distribution → deadlock section → **diff across dumps (identical top frame in all 10 = genuinely stuck)** → follow `owned by "thread-X"` to the real bottleneck → group by name prefix. **`RUNNABLE` ≠ working** — `socketRead0` (external call, no socket timeout) is `RUNNABLE` and invisible if you only count `BLOCKED`. Signature table for `SegmentNodeStore.merge` (write contention), `TraversingIndex` (unindexed query), `AsyncIndexUpdate`, exhausted `qtp*`, slow `sling-oak-observation-*`. Always-present noise: the `ThreadDumpCollector` thread in `dumpThreads0` (observer effect) and Jetty `KQueue.poll`/`Net.accept`. Includes a healthy-baseline worked example (pool growth with no application frames = warm-up, not a leak).
- [jdk-diagnostic-tools.md](infrastructure-ops/jdk-diagnostic-tools.md) — JDK CLI diagnostics against a running AEM (6.5/AMS; **none of them run on AEMaaCS** — Developer Console/Support instead). Attach prerequisites that cause most failures: **same OS user** as the AEM process (`/tmp/.java_pid<pid>` socket; root isn't enough) and a version-matched **JDK, not JRE**. `jps -lv` finds the PID and shows `-Dsling.run.modes` to tell instances apart. **jstack** = execution snapshot: take a **series of 3–5 dumps ~10 s apart**, correlate hot threads via `top -H -p` → `printf '%x'` → `grep nid=0x…` (the mapping AEM's auto-dumps break with `nid=0xffffffff`, see thread-dump-analysis.md); `-F`/`jhsdb` last resort. **jmap** = memory snapshot: `-dump:live` pauses the JVM stop-the-world for the whole write, file ≈ heap size, `live` forces a full GC first; `-histo:live` twice a few minutes apart often names the leak without MAT; production instances should carry `-XX:+HeapDumpOnOutOfMemoryError` instead of 3 a.m. jmap chases. **jcmd** supersedes both (`Thread.print`, `GC.heap_dump`, `GC.class_histogram`, `VM.flags`, `JFR.start` → Mission Control for prod-safe profiling over time). **jstat -gcutil** is the 10-second test for the GC death spiral — old gen ~100% + climbing full-GC count *looks* like CPU in `top` but is a memory problem. Symptom→tool table; cert framing: high-CPU Support case = thread dumps, never heap dumps (STW on a pegged box hurts), bundle list/Sling metrics are distractors.

- [runmode-sources-and-precedence.md](infrastructure-ops/runmode-sources-and-precedence.md) — **Where a runmode comes from, and which half of the set is still mutable.** Five sources — `-Dsling.run.modes`, `sling.run.modes` in `crx-quickstart/conf/sling.properties`, the `-r` start option, the jar filename (`cq5-<mode>-p<port>.jar`), and `web.xml` for app-server deploys — with documented precedence `-D` → `sling.properties` → `-r` → filename. **That precedence only really bites on the first start:** afterwards `sling.properties` holds what was resolved then and the installation modes are frozen regardless, so `-D` cannot flip an installed author to publish (it can only add/drop custom modes) — this doc's reading of how the precedence and freezing rules interact, flagged as such. **Frozen half:** two mutually exclusive pairs, `author`|`publish` and `samplecontent`|`nosamplecontent`, fixed at first start, exit only by deleting `crx-quickstart/` ([production-ready-mode-crxde.md](infrastructure-ops/production-ready-mode-crxde.md)). **Mutable tail:** every custom mode (`dev`, `test`, `golive`, `intranet`, `emea`…) is re-selected at each startup — put anything that must be switchable there. Adobe's "changes to individual configuration properties take effect upon restart" is narrower than it reads: the *mode* freezes, the *config* it selects doesn't. **`install.<runmode>` ≠ `config.<runmode>`:** `nt:folder` carrying bundles/packages vs `sling:Folder` carrying OSGi configs, same matching. On 6.5 `install.<anyCustomMode>` is valid; on AEMaaCS only `install`/`install.author`/`install.publish` exist (no custom runmodes at all), so a 6.5 project relying on `install.dev` has nowhere to land.
- [osgi-config-runmode-resolution.md](infrastructure-ops/osgi-config-runmode-resolution.md) — **Run-mode config folders replace, they do not merge.** A `config.<runmode>` folder is a candidate only if *all* its run modes are active (partial match scores nothing), and among candidates the highest match count wins **the entire PID** — so `config.author` + `config.emea.author` for one PID means the EMEA instance runs the EMEA folder alone, with every property it omits falling back to the **bundle's compiled-in default**, not to the `config.author` value. Silent; only misbehaves on instances carrying the extra run mode. Treat the console as a place to *author* a config and copy into `ui.config`, not as the config itself; on AEMaaCS the route is closed. Two precedence chains and they differ: **startup** `/apps` → `/libs` → `crx-quickstart/launchpad/config`; **runtime** Web Console → `/apps` → `/libs` (with `/libs` masked by `/apps` — the supported way to customize a product config). `/crx-quickstart/launchpad/config` is ConfigAdmin's private store, never edit — and it's why deleting a repo config node doesn't always restore the default. Factory PID separators are era-split: `-<identifier>` (classic `sling:OsgiConfig`/`.config`) vs `~<name>` (OSGi R7 / `.cfg.json`). Audit recipe for drift: `select * from sling:OsgiConfig` (nodes only — file-based configs are `nt:file`, use the `contains(*, '<PID>')` path query).

## dispatcher-url-delivery/

Dispatcher, CDN, URL resolution and the request path: caching rules, SDI, CORS, SSL termination, Sling mappings, exposing APIs.

- [dispatcher-caching-and-invalidation.md](dispatcher-url-delivery/dispatcher-caching-and-invalidation.md) — Dispatcher caching + invalidation + `dispatcher.any` condensed from Adobe docs. **Never cached**: `?` in URI, no extension, `Authorization` header (unless `/allowAuthorized "1"`), non-GET/HEAD, non-200, `no-cache`/`no-store`/`must-revalidate`. Two invalidation paths: **explicit flush** deletes the handle + all `handle.*` siblings then touches `.stat`; **auto-invalidation** (`/invalidate` globs, usually `*.html` only) re-fetches when file mtime < nearest `.stat`. `/statfileslevel N` scopes `.stat` touches to the activated subtree + ancestors (level 0 = whole site); `/statfile` ignored when set; `/gracePeriod` throttles bulk-activation storms; `/enableTTL` (4.1.11+, coexists with `.stat` from 4.3.5), `/serveStaleOnError`. **Flush agent belongs on Publish, not Author** (Author flush races replication → visitor re-caches the old page). Manual flush: `POST /dispatcher/invalidate.cache` with `CQ-Action: Activate|Deactivate|Delete|Test`, `CQ-Handle`, `Content-Length: 0`; body of paths + `Content-Type: text/plain` = delete **and** re-fetch; lock with `/allowedClients`. Load balancing: per-`/statistics` category response scores (max 8), `/unavailablePenalty`, `/stickyConnectionsFor` via `renderid` cookie (sticky paths must be uncacheable), `/failover "1"` + `/health_check`. Evaluation: farms bottom-up, virtualhosts top-down, `/filter` `/rules` `/invalidate` `/allowedClients` **last match wins**; `/clientheaders` is an allowlist; `/vanity_urls` bypasses `/filter`; Author Dispatcher must `deny *` in `/rules`; restart httpd after `/cache` edits. Review checklist of the classic stale-cache symptoms.
- [dispatcher-fundamentals.md](dispatcher-url-delivery/dispatcher-fundamentals.md) — Dispatcher as a **web-server module** (versioned independently of AEM) + the `dispatcher.any` sections the caching note skips. Request flow: cacheable? → cached file under `/docroot` (must equal the web server document root, **one docroot per farm**) → mtime vs `.stat`; **without auto-invalidation/TTL a cached file is served until physically deleted**. Two file-cache gotchas: **body-only cache** — without `/cache/headers` (4.1.11+, no globs; default set incl. Content-Type/Cache-Control; ETag needs Apache `FileETag none`) cached hits carry web-server-guessed headers (MISS correct, HIT wrong Content-Type); and OS filename limits → many-selector URLs silently never cache. Syntax: `$include` with wildcards, `${ENV_VAR}` interpolation. `/virtualhosts`: farms bottom-up, list top-down, full scheme+host+uri match > host-only > catch-all `*` in the **topmost** farm. `/renders`: **`/timeout` default `"0"` = wait forever — always set**, `/receiveTimeout` 600000, `/secure`, `/always-resolve`. `/filter` anatomy: deny-all baseline, last match wins, element rules (`/method /url /query /protocol /path /selectors /extension /suffix`, 4.2.0+) over **deprecated `/glob`** (matches the whole request line = the bypassable form); `"…"` = glob, `'…'` = **regex**; **purge cache after filter changes**; 404-test `/admin /crx /system/console …`. Also `/invalidateHandler` (script per flush: handle/action/scope), `/mode` 0755 ∩ umask, `/serveStaleOnError`. LB internals: ≤ 8 `/statistics` categories (first 8 only), selection = `renderid` cookie → lowest category score → first render; `/unavailablePenalty` (0.1 s units); retries = `/numberOfRetries` 5 × all renders, `/retryDelay` 1 s; `/failover`: 503 → next render, other 50x → `/health_check` arbitrates; `/stickyConnections` `/paths` + `httpOnly`/`secure` cookie flags, sticky paths must be uncacheable. Author Dispatcher: **never cache with Touch UI**, delete cached `/libs`+`/apps` after patches. Debug: loglevel 3→0, **Trace 4 names the blocking filter rule**, `/info "1"` + `X-Dispatcher-Info` header → `X-Cache-Info` verdict. Docs-based Oct 2026.
- [dispatcher-ignoreurlparams.md](dispatcher-url-delivery/dispatcher-ignoreurlparams.md) — Dispatcher `/ignoreUrlParams`: controls which query-string params are cache-relevant (distinct from `/filter`, which is request security, and `/rules`, which is path cacheability). Config shape is a glob allow/deny list like `/filter`, last-match-wins, `/type "1"` = ignore param for cache-key purposes. Two patterns: allowlist-the-ignorable (deny-all baseline + `1` for known tracking params) vs wildcard-ignore-all-deny-the-dynamic (`1` baseline + `0` for the few content-affecting params like search) — the latter is the exam-favored fix when campaign/tracking params vastly outnumber functional ones. Exam trap: offering a `/filter` change as the caching fix — `/filter` is security, not cache optimization.
- [dispatcher-permission-sensitive-caching.md](dispatcher-url-delivery/dispatcher-permission-sensitive-caching.md) — **`/allowAuthorized` is not "cache on/off" — it asks "may the security check be skipped?"** (`1` = treat protected pages as public, serve cached copies to *anyone*; `0` = never skip). Three farm postures: `0` alone = authenticated requests bypass cache entirely (safe, slow — the only case where "0 = don't cache" is true); `1` = blind caching (safe only when all logged-in users see identical content); **permission-sensitive caching** = `/sessionmanagement` (farm-level secure sessions) or `/auth_checker` (per-page HEAD to an AEM authorizer servlet, the AEMaaCS-documented pattern) = *cache once, check each visitor at the door* — and both **require `/allowAuthorized "0"`**; Adobe documents `/sessionmanagement` + `"1"` as **mutually exclusive**. Exam trap (CUG pages not cached despite `/sessionmanagement` added): leftover `"1"` blocks the session gate — the misread is "1 caches *more* so can't be the blocker"; with session management present the gate dominates and unvalidated requests are proxied uncached. Distractor taxonomy: `/rules` = which paths, `/clientheaders` = forwarding (additive answer covered by existing `"*"` changes nothing), `/stickyConnectionsFor` = LB pin taking a *content* path. **Real-world gotcha the exam skips:** CUG login yields a `login-token` **cookie**, so `/header "HTTP:authorization"` never establishes a session — production needs `/header "Cookie:login-token"` too, not just the flag flip. Docs-based, interaction not lab-verified.
- [sling-dynamic-include.md](dispatcher-url-delivery/sling-dynamic-include.md) — Sling Dynamic Include (SDI): keep a page cacheable at dispatcher/CDN while dynamic components (stock price, FX, personalized fragments) stay fresh, no component changes. Servlet filter swaps matched resource types for include placeholders + `nocache` selector dance; SSI (Apache `mod_include`) / ESI (Varnish/CDN) / JavaScript (AJAX) include types; OSGi config options (base path regex, resource types, TTL, selector); limitations (no POST/query-string/suffix components, disable debug comment for non-HTML); when to use vs AJAX lazy-load vs Sling Jobs. Note: "Sling Async Include" is not a real feature name.
- [cors-policy-and-dispatcher.md](dispatcher-url-delivery/cors-policy-and-dispatcher.md) — Browser cross-origin access to AEM lives in **three places that must agree**: the Granite policy factory `com.adobe.granite.cors.impl.CORSPolicyImpl` (full property table: `alloworigin`, `alloworiginregexp`, `allowedpaths`, `supportedheaders`/`methods`, `exposedheaders`, `maxage`, `supportscredentials`), the dispatcher's `/clientheaders` (pass `Origin` + `Access-Control-Request-*` **in**, or the handler never sees an Origin to match), and the dispatcher's `/cache/headers` (cache the `Access-Control-*` **out**, 4.1.1+). **Matching is first-match-wins on Origin × path, and default is deny** (no match denies; *zero* policies denies) — so a broad early policy **shadows** a narrower later one and the symptom is "my new CORS config does nothing," an ordering bug dressed as a broken config. Adobe prefers one policy per origin hostname over broad regexes. **`allowedpaths` are regexes and Adobe's own examples leave `.` unescaped** (`endpoint.json`) — nothing validates them and an over-broad pattern fails **open**. **Authenticated recipe's missed step:** beyond `supportscredentials:true` + `Authorization`/`CSRF-Token` headers, you must add **`/libs/granite/csrf/token.json` to `allowedpaths`** — the client fetches the token cross-origin first, so omitting it fails at the token fetch and points at anything but CORS. **Diagnostic signature: HTTP 200 with no `Access-Control-Allow-Origin` = a CORS denial, not a routing failure** → logger `com.adobe.granite.cors` DEBUG (denial reasons) / TRACE (all requests); replay with curl *including* `Origin`; check auth/CSRF/dispatcher filters aren't rejecting before CORS is consulted. Cacheable on anonymous publish only; flush + restart web server after any change. Includes flagged inference on why multi-origin publish moves up to the dispatcher (one cached response carries one `Access-Control-Allow-Origin`). Ships in `ui.config`, so the replace-not-merge runmode rule applies.
- [ssl-termination-sling-mapping-404.md](dispatcher-url-delivery/ssl-termination-sling-mapping-404.md) — LB terminates SSL + forwards plain HTTP with X-Forwarded-Proto to AEM → all requests 404 unless BOTH fixed: Felix HTTP Service SSL Filter configured to trust the forwarded header (not Granite SSL Connector Factory — that's only for AEM terminating SSL itself), AND Sling Mapping exists at /etc/map/https/host.443 (not just /etc/map/http/host.80). Fixing only the mapping does nothing if AEM never learns the request was HTTPS.
- [sling-resource-resolution-mapping.md](dispatcher-url-delivery/sling-resource-resolution-mapping.md) — `/etc/map`, `sling:alias` and vanity paths as **two opposite operations sharing one config tree**: `resolve()` (URL→resource) and `map()` (resource→URL, i.e. every link AEM renders). **The reverse-mapping trap:** wildcard/regex entries in root-level mappings are silently unusable for `map()` — Sling can't run a pattern backwards — so requests work, links come out as raw internal paths, and people debug the templates. Inbound matching is against a **constructed virtual path `{scheme}/{host}.{port}/{uri_path}`**, which is the entire reason nodes are named `www.example.com.443` and why an instance that thinks it serves HTTP never reads the `https` subtree ([ssl-termination-sling-mapping-404.md](dispatcher-url-delivery/ssl-termination-sling-mapping-404.md)). Longest match, regexes in order, first wins (same shadowing failure as CORS policies); `sling:internalRedirect` is multi-value tried in sequence; `sling:status` default 302. **`sling:alias` surprises:** an alias on `jcr:content` applies to the **parent**, and setting one on both **concatenates** rather than overrides; simple names only; an alias directly on a protected resource may be invisible to restricted principals (put it on a child). **Security — a vanity path can route around auth:** a child of a protected resource with an external vanity path or mapping that isn't a descendant of an existing authentication requirement fails to register that requirement; mitigate with external redirects or manual registration. Audit anywhere vanity paths are author self-service on a tree with protected branches. Vanity knobs (`vanitypath_allowlist`/`denylist`, `maxEntries` default unlimited, `vanity_precedence`, `sling:vanityOrder`) and alias perf knobs (`optimize_alias_resolution`, `allowed_alias_locations`). `$['env':'VAR';default='…']` interpolation works in `sling:match` (not node names) — one of the few per-environment seams when packages can't be environment-scoped. Namespace mangling `jcr:content`↔`_jcr_content`, registered prefixes only. **Test both directions at `/system/console/jcrresolver`** — a mapping that resolves is only half-verified.
- [url-resolution-layers-aemaacs.md](dispatcher-url-delivery/url-resolution-layers-aemaacs.md) — Which layer owns which URL rule on AEMaaCS: CDN → Apache `mod_rewrite` → Dispatcher → Sling resolver (mappings, aliases, vanity paths). Invariant to test: **`resolve(map(resource))` returns the same resource**. Testing only `resolve()` covers half the bugs. - [translation-rules-xml.md](translation-i18n/translation-rules-xml.md) — AEM `translation_rules.xml`: the config-as-code file (priority paths `/conf/global` → `/apps` → `/etc` → `/libs`) that AEM's Translation Configuration UI generates and custom connectors parse to decide translatability. - [translation-connector-cached-services.md](translation-i18n/translation-connector-cached-services.md) — How to implement a translation connector's two JCR-backed hot-path services — the `translation_rules.xml` rules service and the cloud-config/credentials service — so their caches are correct on AEMaaCS. **A `ResourceChangeListener`-invalidated cache needs three mechanisms, not one:** (1) the `ExternalResourceChangeListener` marker, because AEMaaCS author is ≥2 pods on one repository and plain `ResourceChangeListener` "gets only local events" — an edit clears the cache on the writing pod only, so the rules report (routed request) and the XLIFF (Sling job, another pod) disagree, and nothing reproduces locally or on single-node on-prem; (2) an invalidation counter **sampled before the read** and stamped onto the cached value, because `updateAndGet` + `set(null)` loses an event that lands mid-read (a reader CASes null→stale onto an already-cleared cache); (3) a ~60 s TTL backstop for events never delivered at all. Registration traps: the marker does **not** extend `ResourceChangeListener` (implement both, keep registering under `ResourceChangeListener.class` — the marker alone deregisters the listener silently), and a listener with no `resource.paths` is ignored outright. Plus: no `synchronized` (AEM-15) — `AtomicReference` + `AtomicLong`; never cache the credentials failure fallback but do cache "no rules file" (cost: a 4-path `nodeExists` sweep per minute per pod); fetch the ruleset once per pass and thread it through the traversal; context-aware `/conf/<tenant>` lookup turns the cache into a keyed map whose invalidation must be global. Test recipe: aem-mock's `registerInjectActivateService` rejects a `now()`-overriding subclass (`NoScrMetadataException` → hand-wire with `FieldUtils.writeField`), the mid-read race is testable with zero threads via a one-shot `thenAnswer` that fires `onChange` during the load, and the marker needs its own `isAssignableFrom` guard test because nothing else can catch its removal. - [i18n-dictionary-translation-target-path.md](translation-i18n/i18n-dictionary-translation-target-path.md) — A translated i18n dictionary **cannot be written beside its source**: `/apps` and `/libs` are immutable at runtime on AEMaaCS, so `/apps/myproject/i18n/de.json` is an unwritable target and fails at import time, after the vendor has already returned the translation. Adobe: the runtime translation process creates translated dictionaries in `/content/cq:i18n/<projectName>` *"regardless if the source dictionary is stored in /apps or /content"* — the source is only ever read, and Sling merges both locations into one `ResourceBundle`. Adobe's two tools disagree on the shape (translation projects drop `/i18n`: `/libs/wcm/core/i18n` → `/content/cq:i18n/wcm/core/zh.json`; the Translator mirrors the path: `…/search/i18n` → `/content/cq:i18n/…/search/i18n/ar`); lookup ignores the path, so mirror the full folder path, which cannot collide. **Precedence trap:** `/apps` beats `/libs` beats everything else, so a translation in `/content/cq:i18n` is silently ignored for every key a same-language `/apps` dictionary (e.g. a shipped `de.json`) already defines. Adobe docs read Sept 2026; shapes verified on an AEMaaCS SDK author, 6.5 behavior not reproduced.
- [htl-i18n-page-language-gotcha.md](translation-i18n/htl-i18n-page-language-gotcha.md) — HTL `${'…' @ i18n}` resolves its locale as: explicit `locale` option → **containing `cq:Page` language** (`jcr:language` / locale path segment / default **en**) → request locale. - [httpclient-retries-timeouts-aem-connector.md](java-osgi-build/httpclient-retries-timeouts-aem-connector.md) — Apache HttpClient 4.5 is exported by **both** `aem-sdk-api` and `uber-jar` 6.5.22 (verified `unzip -l`, Sept 2026), so a connector needs no vendored HTTP client, just `org.apache.http.*;version=0.0.0` in bnd. **Do not hand-roll the retry loop:** `HttpRequestRetryHandler` covers connection failures (extend `DefaultHttpRequestRetryHandler` so its exception and idempotency rules still apply; with the default `requestSentRetryEnabled=false` a POST is replayed only if it never reached the server, which is what stops a token exchange being submitted twice) and `ServiceUnavailableRetryStrategy` covers `429`/`5xx`; never retry `4xx`. Both are configured per *client*, so a per-call policy (interactive = one attempt, poller = retries) travels in `HttpClientContext` attributes, which both `retryRequest` overloads receive. **The trap:** `getRetryInterval()` takes no arguments — no response, no context, no execution count — so `Retry-After`, exponential backoff and per-call intervals are all inexpressible without smuggling a value through a `ThreadLocal` set in `retryRequest`; decide deliberately, a fixed interval is often fine. **Timeouts are not a ceiling:** connect and read are separate and additive (5+10 = a 15 s call), and the socket timeout is per *read*, so a trickling response runs indefinitely; 4.5 has no total-call timeout and a real one needs a watchdog calling `request.abort()` — which is allowed where `Future.cancel(true)`/`shutdownNow()` are not, since `CQRules:GRANITE-54181` bans interrupting threads, not closing sockets. **Anti-pattern with its own section:** splitting one deadline across two sequential calls (call 1 takes the budget, call 2 gets the leftovers and times out) makes a healthy connection report "did not respond" and throws away an already-successful call; give each call the same timeout instead. Plus the OSGi lifecycle (`@Activate`/`@Modified`/`@Deactivate`, `volatile` client read once per call). From the Phrase TMS connector.
- [sling-path-matches-relative-throws.md](java-osgi-build/sling-path-matches-relative-throws.md) — `org.apache.sling.api.resource.path.Path.matches(other)` is the right "equal to or below" check (`/content-other` false, `new Path("/")` matches everything) but **throws `IllegalArgumentException: Path must be absolute` on a relative argument** instead of returning false, and `ResourceUtil.normalize` keeps relative paths relative. Swapping a hand-written prefix check for it turns a clean 400 on `path=content/acme` into a 500. Fix: check absoluteness at the request boundary before `matches`; keep a relative-path case in the servlet's reject test. Phrase connector, Sept 2026.
- [server-sent-events-in-aem.md](java-osgi-build/server-sent-events-in-aem.md) — Pushing live updates to an author console without polling. AEM does not buffer an SSE response: `text/event-stream` plus `writer.flush()` and `resp.flushBuffer()` per frame streams immediately, chunked. A resource-type-bound servlet answers on any extension (`.sse`), and the login-token cookie carries auth since `EventSource` cannot send headers. Cost is exactly one parked Jetty request thread per stream (measured 1:1), which also holds a JCR session, so cap streams or use `startAsync()`. The trap: a loop with no lifecycle exit survives a bundle stop *and* restart, orphaned forever while keepalives make it look healthy — needs an `@Deactivate` flag (not an interrupt, banned by CQRules:GRANITE-54181) plus a duration cap. Reconnection is weaker than advertised: a non-200 permanently closes `EventSource`, so a redeploy's 404 kills the page until the client implements its own backoff retry. For a dashboard, one channel with a named-event envelope (`name`/`data`/`terminal`) and a bounded queue per subscriber using `offer`, never `put`. On multi-pod AEMaaCS author an in-memory publisher only reaches its own pod's streams: publish from a JCR `ResourceChangeListener` with the `ExternalResourceChangeListener` marker instead.

## ai-integration/

LLM and external service integration with AEM: structured output contracts, service boundaries.

- [llm-structured-output-contracts.md](ai-integration/llm-structured-output-contracts.md) — How an LLM decides what to put in each field of a declared schema, for assistants that must hand validated objects to AEM/Java code instead of prose. **The form model:** three distinct channels — field *names* are the actual specification (a box called `summary` needs no explanation; call it `xyz` and you get garbage), per-field `description` is read at the moment that field is generated (right place for field-local rules like "quote verbatim"), and `instructions`/`input` carry cross-field policy and the facts. **The trap worth internalizing:** with `strict: true`, constrained decoding enforces only *structure* — required keys, `additionalProperties: false`, types, and **`enum` members** (a `Severity` field genuinely cannot return `"sev-1"`) — while range/length keywords are sent in the payload but **not decoder-enforced**; `minItems`/`minimum`/`maximum` are hints, and Pydantic catches violations client-side *after* the call, meaning `responses.parse()` can raise `ValidationError` from inside, so a wrapper guarding only the `None` case is incomplete. Put guarantees you depend on in enums and types; re-check every numeric range in code. **Field order is generation order** — declare `confidence` last so the model scores certainty *after* committing to a cause, not before. **Schema-shaped hallucination:** a required non-empty list (`suggested_actions` with `min_length=1`) instructs the model to invent a remediation step when the context supports none — leave it unconstrained and render the empty case explicitly; keep `min_length=1` only where the caller always supplies enough context to cite (`evidence`). Also: `output_parsed` is `Optional` (raise, don't widen the return type), dump `to_strict_json_schema(Model)` before debugging a prompt, and remember valid ≠ correct — schema validation moves the failure from *unparseable* to *parseable and possibly wrong*, and `confidence` is a self-asserted signal, not a calibrated probability. Verified openai 3.8.0 / pydantic 2.13.5 / Python 3.13, Sep 2026.
- [fastapi-llm-service-boundary.md](ai-integration/fastapi-llm-service-boundary.md) — Putting a validated LLM result behind an HTTP endpoint a Java/AEM client can consume as a DTO, and running it. **Shape:** `contracts.py` (request *and* response models) / `service.py` (prompt + model call + failure translation, no HTTP) / `api.py` (handler that only calls the service) — so the service stays callable from scripts, tests and later agent loops. A `BaseModel` parameter is what makes a JSON *body* (a bare `str` becomes a query param), and the **return annotation `-> AemDiagnostic` is the response model** (explicit `response_model=` still wins when both are present). **Status mapping is the real content:** 422 = client (free, from `Field(min_length=1)`), **502 = the model refused/truncated/failed validation** — the caller did nothing wrong and a retry may work, so 500 misattributes fault and a 200 with a half-built object pushes the failure downstream as valid-looking data — 500 = unanticipated, leave FastAPI's default. That stays a one-line `except` only because the service funnels `output_parsed is None` **and** the `ValidationError` raised from inside `responses.parse()` into one application exception. **Running:** uvicorn is a separate package; `--app-dir` defaults to `""` and uvicorn does `sys.path.insert(0, app_dir)` (`uvicorn/main.py:559`), which is exactly why flat sibling imports resolve only when launched from the app directory. **Traps:** `def` vs `async def` is capacity, not style — FastAPI routes non-coroutine handlers through `run_in_threadpool` (`routing.py:354`) so a blocking SDK call is safe, while `async def` + blocking client stalls every in-flight request; the price is anyio's default **40**-token thread limiter = 40 concurrent model calls, the real throughput ceiling. `Field(description=...)` written *at the model* is copied verbatim into `/openapi.json` and becomes public API docs. **Codes you raise are not codes you document** — the generated schema lists only 200/422, so a generated Java client has no branch for the 502 unless you declare `responses={502: ...}`. Enums and `ge`/`le` do survive into the published schema (one declaration constrains decoding, validates the reply, documents the API), but note the asymmetry from [llm-structured-output-contracts.md](ai-integration/llm-structured-output-contracts.md): only the enum is decoder-enforced. Verified fastapi 0.141.1 / starlette 1.6.0 / uvicorn 0.53.0 / pydantic 2.13.5 / anyio 4.15.0 / Python 3.13.2, Sep 2026.

## fundamentals/

Beginner-level mental models for concepts the dense docs assume, each ending in the AEM consequences with links onward.

- [ip-addresses-explained.md](fundamentals/ip-addresses-explained.md) — IP addresses via the mailbox picture: an IP is "where to send the letter" (and the return address); DNS is the phone book (A = name→number, CNAME = alias, **apex can't be a CNAME** — why Cloud Manager wants four A records for bare domains but a CNAME for subdomains); private ranges (`192.168.*`, `10.*`, `172.16–31.*`) are room names that don't route outside, NAT is the receptionist, so one office = one public IP = feasible allow lists; **IP allow list = doorman's guest list**, canonical failure = a legitimate service turned away with the burglars (Screens starved by a publish allow list); **CIDR**: `/24` = 256 addresses not 24, smaller suffix = bigger block, `/32` = one; IPv4 (~4.3 B, exhausted, hence NAT) vs IPv6 (`AAAA` records — an IPv4-only allow list treats IPv6 clients differently, silently); IP delivers letters, TCP makes them a conversation, **ports are apartment numbers** (`:443`, `:4502`, `:8023` standby sync) — IP+port is the full address.
